# Code Review: Axon Desktop Whiteboard

**Дата**: июль 2026
**Объём кодовой базы**: ~6500 LOC (TypeScript/TSX), 30 исходных файлов
**Результат сборки**: `tsc --noEmit` PASS, `eslint` PASS, `vitest` 118/119 PASS (1 timeout — среда исполнения)

---

## 1. Executive Summary

**Общее состояние**: Кодовая база высокого качества для desktop-приложения такого объёма. TypeScript strict mode, Zod-валидация, корректная IPC-безопасность, атомарная запись файлов и рабочая система recovery свидетельствуют об инженерной дисциплине. Архитектура чётко разделена на слои (model → rendering → editor → ui), зависимости минимальны и оправданны.

**Основные проблемы**:
- Производительность деградирует на документах с изображениями из-за многократной полной сериализации при каждом редактировании, проверке dirty и commit
- Потенциальный краш при копировании orphan-узлов mind map через `copySubset`
- Класс `Editor` (570 строк) является god-объектом, смешивая UI-состояние, операции с документом, управление вкладками и буфером обмена

**Критических проблем безопасности не обнаружено.** Валидация IPC-отправителя, sandbox, CSP и проверка входных данных реализованы корректно.

## 2. Critical / High Issues

### HIGH-1: Потенциальный краш в `copySubset` при обходе дерева mind map

**Файл**: `src/model/operations.ts:166-173`

```typescript
const map = new Map(objects.map((o) => [o.id, o]));
for (const o of objects)
  if (o.type === "shape" && o.mind) {
    let root = o;
    while (root.mind?.parentId)
      root = map.get(root.mind.parentId) as typeof o;
    o.mind = { ...o.mind, treeId: root.id };
  }
```

**Проблема**: Если в выделении есть дочерний узел, чей `parentId` тоже в выделении, но *дедушка* — нет, то `parentId` родителя обнуляется на строке 161. Однако порядок обработки массива `objects` случаен. Если ребёнок обрабатывается *до* родителя, его `parentId` всё ещё указывает на родителя (который в `map`), обход продолжается к родителю, а затем проверяет `parent.mind.parentId` — **оригинальное** значение, не обнулённое. Если дедушки нет в `map`, `map.get()` возвращает `undefined`, и следующая итерация крашится на `undefined.mind`.

**Почему это проблема**: Копирование/вставка промежуточного узла mind map может уронить приложение.

**Критичность**: HIGH — краш приложения при определённом сценарии.

**Исправление**: Добавить защиту от отсутствующего родителя:
```typescript
while (root.mind?.parentId) {
  const parent = map.get(root.mind.parentId);
  if (!parent || parent.type !== "shape" || !parent.mind) break;
  root = parent;
}
```

### HIGH-2: Двойная `JSON.stringify` при каждом редактировании

**Файл**: `src/editor/store.ts:199-201`

```typescript
commit(before: AxonDocument, after = this.state.doc) {
  if (JSON.stringify(before) !== JSON.stringify(after))
    after = { ...after, version: 3 };
```

**Проблема**: Каждое редактирование сериализует оба документа (до и после) в JSON для сравнения. Документы могут содержать base64-изображения до 28 МБ каждое. Даже с несколькими изображениями каждое редактирование вызывает многомегабайтную сериализацию дважды.

**Почему это проблема**: Прямая задержка ввода. Набор текста в документе с изображениями будет ощущаться медленным, поскольку `updateText()` → `endText()` → `commit()` → двойная `JSON.stringify`.

**Критичность**: HIGH для документов с изображениями; LOW для документов без изображений.

### HIGH-3: `serializeDocument` повторно валидирует через Zod

**Файл**: `src/model/document.ts:398-400`

```typescript
export function serializeDocument(doc: AxonDocument) {
  return JSON.stringify(parseDocument(doc));
}
```

**Проблема**: `serializeDocument` вызывает `parseDocument`, который выполняет полную Zod-валидацию (включая дорогой `superRefine` с обходом ancestry mind map) перед сериализацией. Эта функция вызывается в:
- `isDirty()` (при каждом рендере через `dirtyCache`)
- `workspace.update()` (при каждом IPC-вызове `axon:update`)
- `workspace.add()` (начальный расчёт dirty)
- `workspace.save()` (для флага dirty)
- `workspace.restore()` (для каждой вкладки)

**Почему это проблема**: `superRefine` строит Map'ы, обходит цепочки предков и проверяет количество ветвей — всё ради сериализации документа, который уже прошёл валидацию. Это единственное самое дорогое узкое место производительности.

**Критичность**: HIGH — системная проблема, влияющая на все операции.

## 3. Производительность

### PERF-1: `snap()` пересчитывает bounds всех объектов при каждом движении мыши

**Файл**: `src/model/snapping.ts:24-42`

Во время перетаскивания `snap()` перебирает каждый неисключённый объект, вызывая `objectBounds()` для каждого. Для коннекторов `objectBounds()` вызывает `route()`, генерирующую до 65 точек кривой Безье. С 500 объектами (приложение позволяет до 10 000) это ~32 500 вычислений точек на событие `pointermove`, срабатывающее с частотой 60–120 Гц.

**Масштабируемость**: При 1000 объектах snapping alone может занимать >5 мс на кадр, вызывая видимые подтормаживания при перетаскивании.

**Исправление**: Предварительно вычислить bounds для всех неисключённых объектов один раз при начале перетаскивания, кэшировать их и пересчитывать только для изменившихся объектов.

---

### PERF-2: `expandSelection()` строит Map'ы при каждом вызове

**Файл**: `src/model/operations.ts:9-63`

Вызывается при каждом движении мыши во время перетаскивания (через `useGestures.ts:189`). Заново создаёт `byId`, `groups`, `children`, `branches` Map'ы. Для 1000 объектов это ~4000 записей Map на кадр.

**Исправление**: Кэшировать adjacency-структуры при изменении документа или хотя бы при начале перетаскивания.

---

### PERF-3: `isDirty()` триггерит сериализацию для каждой вкладки при каждом изменении состояния

**Файл**: `src/editor/store.ts:170-181`

`App.tsx:58` вызывает `editor.isDirty()` при каждом рендере. Заголовок вкладки также вызывает `editor.isDirty(id)` для показа индикатора «грязной» вкладки (строка 470). Для 10 открытых вкладок с документами, содержащими изображения, это может сериализовать 10 документов за цикл рендера.

---

### PERF-4: `contentBounds()` рендерит шрифтовые пути для измерения текста

**Файл**: `src/rendering/primitives.ts:206-219`

Для экспорта и `fit()` `contentBounds()` вызывает `fontFor(o.style).getPath(...)` для каждой текстовой строки каждого объекта. `opentype.js`'s `getPath` генерирует SVG path data для каждого глифа — это полный проход рендеринга шрифта, а не просто измерение ширины. С 100 текстовыми объектами по 3 строки это 300 вызовов рендеринга шрифтов.

---

### PERF-5: ObjectView memo-сравнение слишком слабое для коннекторов

**Файл**: `src/rendering/ObjectView.tsx:96-101`

```typescript
(a.object.type === "connector"
  ? a.doc === b.doc
  : a.doc.background === b.doc.background && a.doc.assets === b.doc.assets),
```

Для коннекторов memo-проверка требует `a.doc === b.doc` (ссылочное равенство). Поскольку `Editor.set()` создаёт новый объект doc при каждом изменении состояния, **все** коннекторные ObjectView перерендериваются при каждом изменении состояния, даже если изменилось только выделение.

**Масштабируемость**: С большим числом коннекторов каждое изменение выделения перерендеривает все из них.

## 4. Архитектура

### ARCH-1: Editor — god-класс (572 строки)

**Файл**: `src/editor/store.ts`

Класс `Editor` обрабатывает:
- Жизненный цикл вкладок (`acceptSession`, `activate`, `closeSession`, `snapshots`)
- Мутации документа (`change`, `commit`, `preview`, `patchObject`)
- Управление историей (`undo`, `redo`)
- Выделение (`select`, интеграция с `expandSelection`)
- Управление стилями (`style`, `formatChange`, `resetStyle`, `useStyleForNew`)
- Редактирование текста (`beginText`, `updateText`, `endText`)
- Буфер обмена (`copy`, `paste`)
- Mind map (`topic`, `newObject`)
- Настройки (`preferences`)
- Навигация (`fit`, `zoom`)
- Работа с изображениями (`addImage`)
- Операции с объектами (`remove`, `duplicate`, `group`, `lock`, `order`, `align`, `move`)

**Влияние**: Сложно тестировать изолированно, сложно рассуждать о потоке состояния, любое изменение рискует побочными эффектами в несвязанном функционале.

**Рекомендация**: Не срочно — класс работает. Но для удобства поддержки стоит рассмотреть извлечение:
- `TabManager` (жизненный цикл вкладок, snapshots)
- `DocumentMutator` (change, commit, preview, undo/redo)
- Сохранить `Editor` как координатор/фасад

**Файл**: `electron/main.ts`

Коллбэк `app.whenReady()` определяет все IPC-хэндлеры инлайн, вместе с настройкой меню, созданием окна, инициализацией сессии и обработкой изображений. Нет разделения между:

### ARCH-3: Zod `superRefine` содержит сложную бизнес-логику

**Файл**: `src/model/document.ts:119-246`

Валидация mind map (обход ancestry, обнаружение циклов, подсчёт ветвей, проверка согласованности сторон) реализована внутри Zod-схемы. Это 127 строк императивного кода внутри декларативного определения схемы.

**Влияние**:
- Сложно тестировать отдельные правила валидации

- Сообщения об ошибках общие («Повреждённая структура mind map») без указания, какие объекты проблематичны

## 9. Рекомендуемый рефакторинг

### Приоритет 1: Устранить повторную Zod-валидацию при сериализации

**Эффект**: Устраняет узкое место №1 производительности. Каждая операция, вызывающая `serializeDocument`, перестанет выполнять полную валидацию документа.

**Подход**: Создать `serializeValidDocument(doc)` без повторной валидации, сохранить `parseDocument` только на границах ввода (загрузка файла, IPC).

---

### Приоритет 2: Защитить `copySubset` от отсутствующих родителей

**Эффект**: Устраняет потенциальный краш при копировании узлов mind map.

**Подход**: Добавить null-guard в while-цикл обхода дерева.

---

### Приоритет 3: Вынести magic numbers в именованные константы

**Эффект**: Единая точка изменения лимитов, улучшенная читаемость, предотвращение рассинхронизации лимитов в разных файлах.

**Подход**: Создать `src/shared/limits.ts` с экспортом `MAX_DOCUMENT_BYTES`, `MAX_IMAGE_BYTES`, `MAX_TEXT_LENGTH`, `MAX_OBJECTS`, `MAX_TABS`, `MAX_COORDINATE`.

---

### Приоритет 4: Кэшировать bounds объектов при перетаскивании

**Эффект**: Устраняет O(n) вычислений на каждый `pointermove` во время drag. Критично для документов с 500+ объектами.

**Подход**: Предвычислить bounds для всех объектов при начале жеста, хранить в состоянии жеста, пересчитывать только для изменившихся объектов.

---

### Приоритет 5: Очистить `Editor.style()` поток управления

**Эффект**: Улучшенная читаемость, устранение мёртвого кода.

**Подход**: Разделить на два явных пути: применение стиля к выделенным объектам и обновление дефолтов инструмента.

---

### Приоритет 6 (при росте кодовой базы): Разделить `Editor` на подмодули

**Эффект**: Улучшенная тестируемость, более чёткие зоны ответственности.

**Подход**: Извлечь `TabManager` и `DocumentMutator`, оставив `Editor` координатором.

---

### Приоритет 7 (при росте кодовой базы): Структурировать `electron/main.ts`

**Эффект**: Улучшенная навигация, возможность unit-тестирования отдельных хэндлеров.

**Подход**: Разделить на `handlers/`, `menu.ts`, `session.ts`.

## 11. REQUIRES MANUAL DECISION

Архитектурные или спорные изменения, где существует несколько разумных вариантов реализации:

1. **Разбиение класса `Editor`** — Класс большой, но когерентный. Извлечение `TabManager` или `DocumentMutator` улучшит тестируемость, но добавит косвенности. Стоит делать при дальнейшем росте кодовой базы, но не срочно для текущего размера.

2. **Рефакторинг `electron/main.ts`** на отдельные модули (хэндлеры, меню, управление сессиями) — Улучшает организацию, но меняет структуру проекта. Стоит делать вместе с чёткой конвенцией именования модулей.

3. **Кэширование bounds объектов при перетаскивании** — Требует хранения предвычисленных bounds в состоянии жеста. Кэш нуждается в стратегии инвалидации. Средняя сложность, высокий выигрыш в производительности для больших документов.

4. **Вынесение валидации mind map из Zod `superRefine`** в отдельную функцию — Улучшает тестируемость и отлаживаемость, но означает, что валидация больше не соколокирована со схемой. Может быть функция `validateMindMap(doc)`, вызываемая из `superRefine`.

5. **Замена/обновление `opentype.js`** — Шрифтовой рендеринг используется для текстовых контуров в SVG/PDF-экспорте. Обновление может изменить метрики глифов. Требует визуального регрессионного тестирования.

6. **Добавление fast-path для dirty-checking через `JSON.stringify`** — Можно использовать хеш вместо полной сериализации, но требуется аккуратная обработка порядка ключей JSON. Альтернатива — отслеживание мутаций на уровне объектов для избежания полного сравнения документов.
