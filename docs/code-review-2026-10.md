## 3. Новые архитектурные решения

### 3.1. Система индексов (`src/model/indices.ts`)

**WeakMap-кэш adjacency-структур** по immutable-массиву объектов документа. Один вызов `getDocumentIndex` строит `byId`, `order`, `groups`, `children`, `branches`, `dependentConnections` — и кэширует результат. `cacheDocumentIndex` переиспользует топологию при геометрических изменениях (move, resize), не перестраивая индексы.

**Эффект**: `expandSelection` больше не строит Map'ы на каждый вызов. Для 9000 объектов — снижение с ~2 секунд до единиц миллисекунд на повторных вызовах.

### 3.2. Инкрементальный dirty-checking (`src/model/content.ts`)

`DocumentContentState` отслеживает различия между текущим и сохранённым документом на уровне отдельных объектов и assets. При мутации одного объекта проверяется только он, а не весь документ. `isDirty` возвращает O(1).

**Эффект**: Для документов с изображениями (до 28 МБ base64 на объект) dirty-checking стал мгновенным. Было: ~590 мс на 1000 объектов с тремя PNG. Стало: ~0.28 мс.

### 3.3. Минимальные проекции для рендеринга (`src/rendering/dependencies.ts`)

`objectRenderDocument` создаёт минимальный `AxonDocument` для каждого объекта, содержащий только сам объект, его привязанные endpoints и asset. WeakMap-кэш по immutable-объекту. Memo в `ObjectBody` теперь сравнивает проекции, а не полный документ.

**Эффект**: Изменение несвязанного объекта больше не перерендеривает все коннекторы.

### 3.4. Сериализация без валидации (`src/model/serialization.ts`)

`serializePreparedDocument` строит явный DTO с контролируемым порядком ключей, без Zod-парсинга. Используется для внутренних операций (dirty-checking, recovery, clipboard). Публичная `serializeDocument` сохранена для границ ввода.

**Эффект**: Внутренние сериализации больше не платят стоимость полной Zod-валидации с `superRefine`.

### 4.2. Оставшиеся узкие места

**PERF-A: Snap продолжает линейный поиск** — `snap()` по-прежнему перебирает все подготовленные bounds для поиска ближайшего совпадения. С подготовленными targets это O(n) на каждый move, но без повторного вычисления bounds. Для 9000 объектов — ~3.4 мс, приемлемо для текущих сценариев.

**PERF-B: Полная Zod-валидация при загрузке файлов** — `parseDocument` по-прежнему выполняет полную валидацию при чтении файлов. Это правильно для границ ввода, но для документов с 9000+ объектами может занимать ~70-90 мс.

**PERF-C: IPC передаёт полные документы** — Контракт и частота (debounce 120 мс) не изменены. Для документов с изображениями это потенциально большие payload'ы.

## 11. REQUIRES MANUAL DECISION

1. **Пространственный индекс для snap** — При реальном росте до 10000+ объектов линейный поиск bounds станет проблемой. R-tree или grid-индекс добавят сложности. Требуется профилирование на реальных сценариях.

2. **Delta-протокол IPC** — Передача только изменённых объектов вместо полного документа. Снижает трафик, но усложняет контракт и восстановление при пропущенных обновлениях.

3. **Ленивая валидация при загрузке** — Для очень больших документов можно валидировать по частям или отложить до первого редактирования. Риск: пропуск ошибок в невалидированных частях.
